# Crew Lab SI 社群編輯準則

本文件是 Crew Lab SI 社群選題與寫作的唯一正式準則。每次編輯工作開始時，先從 `magic76/crew-social-agent` 的 `main` 讀取本文件，再開始選題或寫稿。其他 skill、檢查表與排程負責流程、資料欄位、查證及安全；若其中的寫作建議與本文件衝突，以本文件為準，並只調整衝突的編輯文字，不變更研究、證據、產物格式、發布授權或安全規則。

## 選題從讀者價值開始

先找有證據的真實事件、困擾、決策或發現，判斷它對讀者有什麼具體價值。只有功能更新、PR、課程數字或通用摘要，而沒有可說的故事或收穫，應淘汰或暫緩。不要為了篇數重複介紹網站或產品。

小更新可以累積；當數個彼此相關、可核實的變化共同解釋一個問題、決策或發現時，可以整理成完整故事。不要為湊稿把互不相關的變更硬接在一起。

## 從「讀者也能做到」選題（2026-11-15 起）

優先挖掘：一般人本來以為很難、很貴、不會寫程式或只能靠專業人士做的事，現在能藉 AI 以低門檻嘗試；AI 解決生活中真實的小麻煩；以及真實、出人意料但能讓讀者理解的實驗。從「讀者想完成什麼、在哪裡卡住」尋找證據，再選擇是否使用 GitHub 專案、原始研究或新聞素材；不要只因有 commit、PR 或模型更新就反推一篇貼文。

優先用三種可選敘事角度，而不是每篇照模板寫：
- **外行人也能試**：具體成果、成本與必要條件、最少可操作步驟；教學必須可核實，未實測不得寫「我試過」或保證成功。
- **AI 改造真實生活**：普通人熟悉的場景、原本的麻煩、實際做出來的結果；產品名稱、技術堆疊和架構放後面。
- **有趣實驗／意外結果**：明確交代原本想做什麼、實際發生什麼、為何值得一看；失敗也有價值，但不得編造情節或結果。

AI 新聞與研究仍可入選，但必須能回答「這件事會幫讀者省掉什麼麻煩、做成什麼事、或改變什麼判斷？」若沒有答案，寧可留在研究報告，不強行轉成社群文。

選題比例作為下一階段實驗假設：**40% 低門檻實作教學、30% 生活改造、20% 趣味實驗與開發故事、10% 新聞研究**。按多日觀察，不是每日硬配額；選題先看故事證據與品質，禁止為滿足比例而湊稿或將同一題重複包裝。2026-11-05～11-14 已進行的試驗保留原始分布作為歷史基準；自 2026-11-15 起標示策略變更，分析時區分前後期，不把混合期間的比較當成因果證據。

## 讓故事帶路

從證據最扎實、最具體的情境、困擾、決策或發現開場。產品背景不是固定前言；讀者需要時，用一句白話順帶說明即可，位置依故事安排。不得要求每篇先介紹專案再說事件。

寫清楚為什麼做、遇到什麼、最後發現或決定了什麼。避免逐項列功能或照抄 PR 摘要。不要固定標題、口頭禪、hashtag、反轉句或結尾提問。

審核紀錄中的 `reader_context` 是理解素材的欄位，不是貼文開頭的格式要求，也不必逐字放進文案。

## 每篇都要有「所以呢」

Facebook 和 Threads 的每個版本，都要在可查證的事實之後，至少用一句具體說明這件事對讀者的意義，或讀者可以拿來做什麼。不要只列數字和限制就停下來。例如談接案工作組合的變化，可以提醒接案者報價時把提示、資料處理、驗收和溝通拆開估算；這是編輯建議，不能冒充來源證明的成效或個人實測。

必要的限制聲明仍要保留，以簡短句子放在後段，不要讓限制成為結尾的主要訊息。依故事自然安排語句，不必真的寫出「所以呢」，也不強制固定句型。缺少具體讀者意義或可採取行動的稿子不得通過編輯審核；補寫後再審，無法有根據地補寫時就暫緩。

## 產品提及、來源引用與導流分開

預設不提網站或產品，貼文正文不放網址。內容首先讓讀者得到具體收穫並願意追蹤帳號；連結點擊不是每篇內容的目標。不要為了導流硬塞產品名、試用邀請或 CTA。感興趣的人可從個人檔案認識網站，不必每篇提醒。

一週最多兩篇貼文可以提到 Crew 網站或產品，而且故事主題本身必須直接關於該產品，並有可追溯的真實素材支撐，例如有紀錄的使用者情境、實際操作中的發現或產品決策。單有 PR、功能更新、課程數字或泛泛的產品相關性，不足以取得提及額度。預設不提；一旦本週額度用完，其他稿件都省略網站與產品提及及產品連結。

額度按台北時間週一至週日計算；一個故事主題的 Facebook 和 Threads 版本合計一篇。定稿並選入當週 review 的貼文若在正文提及自家網站／產品，或在首則留言放自家產品連結，就算一篇；不因平台版本重複計數。每篇只記一個是否提及的欄位，並填入提及的平台、位置與產品名稱，方便計算本週比例。

若故事確實需要產品連結，只放首則留言，不放正文；不必為了導流在正文呼籲點擊。來源引用照現有規則放首則留言。純粹為查證而引用的來源名稱與來源 URL 不算產品提及或導流；若同一留言另外包含自家產品連結，仍算產品提及。

每日 review 需保留週起訖日、當週已選入的主題數、含網站／產品提及的主題數、比例與剩餘額度。將同週過往 review 中可確認的稿件納入統計；舊紀錄無法確認時標示涵蓋不完整，不要猜。實際流量只依已核實發布的貼文和平台資料比較：在每個實際發文平台記錄是否提及，再對照觸及、新追蹤與網站點擊；相近的平台、題材、時段及貼文齡才適合並列觀察，不能把小樣本差異寫成因果。

## 事實與進度狀態要精確

所有可核實主張都要有可追溯的來源或專案證據，保留發布日期與完整 URL。不得編造使用經驗、用戶對話、測試結果、成效、情緒或數據，也不得把假設寫成已發生的故事。

清楚區分程式碼／內容已修改、PR 已合併、測試或實際操作已驗證，以及網站正式上線。commit 或合併狀態本身不能證明測試、部署或使用成效。

個人觀察只有在使用者提供或有紀錄支持時才能用本人語氣表達。可用幽默和吸引人的開場，但不能誇大證據。

## 先讓一般人看得懂

除既有真實性與讀者收穫外，編輯每篇時要用「滑過去 3 秒」檢查：不懂 AI、沒看過 Crew 的人能不能立刻理解主角想做什麼？成果是否具體到能想像、能分享給朋友，或看完就想自己試一次？

標題和開頭優先講看得見的結果或生活衝突，而非技術名詞、角色代號、模型規格、提交紀錄。不要強制每篇採用「不會寫程式也能…」、數字步驟、誇張問句或固定反轉；故事／教學／短觀察可有不同節奏。避免把示範建議寫成作者已完成的親身經歷。

## 出稿自檢

每篇定稿前，逐項問：

1. 刪掉產品名和網址後，這篇仍值得讀嗎？
2. 和近期文章是否重複題材、開場或結論？
3. 讀者看得懂發生什麼事，並能帶走具體收穫嗎？
4. 每個平台版本在事實後，是否至少有一句具體交代讀者意義或可做的事？必要限制是否簡短地放在後段，而非成為結尾主軸？
5. 一般人在 3 秒內看得懂情境嗎？看完會想試、想收藏、想分享，或有新的實用發現嗎？
6. 是否有具體、可核實的成果或可跟做步驟？若是提案／假設，是否明確標示未實測？

若答案顯示內容只是公告、摘要、導流或沒有證據的推測，改選題、補足可核實的故事，或暫緩。

## 配圖標準

若有真實可公開的產品截圖、操作照片、螢幕錄影畫面或真正的前後對比，優先評估使用這些原始證據；教學可用真實操作步驟畫面。保護個資、金鑰、私人畫面和第三方權益。真實素材不適合時再考慮情境插畫；插畫不能冒充真實操作、成果或 UI。

圖片要呈現這篇故事的關鍵情境或衝突，不能只放一個象徵物件。先有故事，再決定要不要配圖；若純文字更清楚，就保留純文字。

畫面要有能說明事件的場景、細節和視覺層次，讓人一眼看出角色、目標與衝突。Crew Cloud 吉祥物可以作為配角；故事不需要時就不放。圖片上放一句繁體中文短標題，在動態牆快速滑過時能看懂重點。以 4:5 手機直式 1080×1350 製作，主標題要有足夠對比、安全留白；避免依賴手機上讀不清的小字。

禁止假截圖、假數據，以及會讓人誤以為是產品宣傳的構圖。概念插畫不得冒充實際測試、介面或產品畫面。Queue 的 alt text 與圖片 metadata 要明確說明這是插畫或示意圖，並準確描述畫面。

出圖前先遮住標題或不讀畫面文字，問：「不看文字，這張圖能讓人猜到主題嗎？」若看不出故事事件或衝突，就重做、改用真實且可分享的素材，或不配圖。不要為了數量生圖。

## 與既有流程的關係

本準則規範選題、寫法與社群配圖標準；不改變研究報告、候選 review 欄位、Queue schema、時段、發布核准、Local Publisher 或影片交接。依現有要求保留 claim→evidence、review、來源首則留言、平台版本、排程與安全檢查；通過編輯審核不等於發布授權。
